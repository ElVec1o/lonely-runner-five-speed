# Reproduction directory: the five-speed spectrum theorem in Lean 4

All paths are relative to this directory (`repro/`). The Lean project is `../lean` (override with `LEAN_DIR`).
Labels: **observed** = run on 19 November 2026 on the development machine (macOS, 24 GB, 10 cores) and the output read; **quoted** = a figure from the development records, not re-run for this directory; **not done** = not run.

## 1. What is claimed
`LRSpectrumFull.L5S5.five_speed_spectrum_final` (module `LRSpectrumFull/L5S5/FiveSpeedFinal3.lean`): for `v : Fin 5 -> Int` with all entries positive, `v` injective and `ML v < 1/5`, there is an integer `s >= 1` with `ML v = s/(5s+1)`. No hypothesis is left over.
`LRSpectrumFull.L5S5.five_speed_spectrum_iff_final` (module `FiveSpeedFinal4.lean`): for `x : Real`, `x` is the `ML` of five distinct positive integer speeds with `x < 1/5` iff `x = s/(5s+1)` for some integer `s >= 1`. `five_speed_attained` (module `FiveSpeedOfTree.lean`): `ML(1,2,3,4,5s) = s/(5s+1)`.
`ML v = sSup_t min_i dist(v_i t, Z)` (`MaxLoneliness.lean`, `NearestInteger.lean`: read these two files, 218 lines, before trusting the English; `check_axioms.lean` prints the definitions with `#print`).
Not claimed: repeated, zero, negative or non-integer speeds, other numbers of speeds, shifted versions, values `>= 1/5`, any first proof (see the paper, section on prior art; Yi, Gill and Bu, arXiv:2610.40694v1, reduce five speeds to norm below 33,750 and do not enumerate the rest; this work is a complete kernel-checked proof, not a claim of priority), peer review.

## 4. Requirements
* `elan` with the toolchain above, the Mathlib cache for the pinned revision, Rust (cargo, std only, no crates, `--offline`) for `regen_data.sh`, `rsync`, `shasum`, `python3` (only `tools/closure.py`, a 20-line import walker, seconds).
* Machine: one `lean` worker of this project peaks between about 4 and 10 GB (rollout per-representative peaks 3.4 to 5.7 GB, `EXPECTED_rollout.tsv`; the heaviest earlier modules reached 8.9 to 10 GB); the development machine has 24 GB. `lake` has no `-j` flag. **One lean process at a time.** Never run a bare `lake build` (lake starts one worker per core; a whole-tree build reached 29.6 GB on the development machine).
* Disk: oleans, ileans and C files of 17,598 modules plus Mathlib's cache; the development `.lake/build` was 13.8 GB at one point; keep at least 20 GB free for a from-scratch build (estimate; not measured for a clean tree).
* Time: a from-scratch `build.sh --run` is about **36.8 h** of Lean time (leaf-rollout cost model, quoted; the rollout driver's recorded CPU sum for the 1,965 per-representative chains is 30.1 h, wall 40.2 h, 12,713 modules, maximum peak 5,666 MB, in `inputs/rollout_results.tsv`, summarised in `EXPECTED_rollout.tsv`), plus lake start-up per call (observed on a built tree: 1 to 2 s for per-representative modules, 8 to 10 s near the root, `expected_output/time_lake.tsv`). It was **not run**; no clean from-scratch rebuild of the five-speed closure has been done.

## 6. Building: the supported route
```
bash build.sh --plan                 # validate: sources present, sha256 = MANIFEST, order topological, pins, disk; no lake
bash build.sh --by-group             # module counts and manifest index ranges by directory
bash build.sh --status               # ONE `lake build --no-build ...FiveSpeedFinal4` (a built tree prints `All targets up-to-date (20192 jobs)`)
bash build.sh --run                  # build all 17,598 modules, one `lake build` each, resumable (about 36.8 h, not run)
bash build.sh --run --from 400 --to 900   # a range;  --only L5S5.FiveSpeedFinal4  selected modules;  --force
```
In the shipped state `build.sh --plan` reports `PLAN INCOMPLETE` (exit 4): the 9,312 shipped modules are valid and the 8,286 omitted generated modules are missing. After `regen_data.sh --full --install --steps build,v3,s4o,lines` it reports `PLAN VALID`.

**Order by driver** (manifest index ranges: `bash build.sh --by-group`): (1) base modules, `L5S3`, `L5WP1`, the hand-written `L5S4` library modules (`LinRCore`, `LinRSound`, `LinRGlue`, `Sym`, `ChainRep`, `Records`, T4/T2 machinery): about 400 modules; (2) per depth-two representative `rep` of the 1,965: `GD3N<rep>` (node data) and `GD3F2N<rep>`, optionally `GD3N<rep>M<k>`, `GD3N<rep>Z`, then `GD3O<rep>T`, `GD3O<rep>Rc<k>`, `GD3O<rep>` (the development rollout built exactly this, bottom-up, one module at a time, 12,713 modules); (3) the lines stage: `LinRQSC<k>` chunks, group and node assemblies, `LinRAll`, `LinRCov`, `LinRFinal`; (4) `L5Reg.Reg<rep>`; (5) the aggregation `AggFive.*`, the mirror `AggFive.Hl.*` and `AggFive.Clean.*`; (6) `L5S5`, ending in `FiveSpeedFinal3` and `FiveSpeedFinal4`. `build.sh` itself follows the manifest order, so this list is only a map.

`build.sh` waits for a memory gate (RSS of all lean processes + `GATE_RESERVE_MB` <= `GATE_LIMIT_MB`, defaults 9500/18000), takes an atomic lock directory, checks that every project import of a selected module is recorded OK in the results table or selected earlier, runs lake through an optional watchdog wrapper (`WRAPPER=...`, called as `WRAPPER CEILING_MB LOGDIR NAME cmd...`; default none, which is not recommended), writes one row per module to `logs/build_results.tsv` (so a second `--run` resumes), and retries a kill (exit 137 with no `error:` line) after 600 s. It aborts on a real `error:` line or on a kill by its own watchdog, because later modules would then import an unbuilt module and lake would rebuild unbuilt imports in parallel. Exit codes: 0 done or plan valid, 1 error, 2 plan invalid, 3 disk or lock, 4 omitted generated sources missing.
Observed on the built development tree: `--plan` PLAN VALID in 7 s (17,598 sources, 0 missing, 0 sha256 mismatch, 0 order violations); negative controls: a corrupted hash of a hand-written module gives PLAN INVALID (exit 2), a corrupted hash of an omitted-family row gives PLAN INCOMPLETE (exit 4), an index swap gives 5 order violations and exit 2; `--run --only NearestInteger,MaxLoneliness` built both in 1 s each, a second run skipped both (resume), and a run on a module whose import is not recorded aborted with a clear message. A test assembly of the repository layout in a scratch directory gave `--plan` exit 4 with 0 in-repository problems, and `lake build --no-build` resolved a module target in that layout.

16 GB machines: the heaviest modules are the `L5S4.GD3O<big rep>` chunk modules and the lines chunks; their peaks in the rollout were at most 5.7 GB, but earlier line modules reached 8.9 to 10 GB; set `GATE_LIMIT_MB=16000 GATE_RESERVE_MB=9500` and close everything else. Below 12 GB do not try.

## 7. Regenerating the generated Lean (`regen_data.sh`)
`bash regen_data.sh --steps build,v3,s4o,lines` (sample mode, 14 representatives and 3 slices of the lines plan, about 20 s) builds the Rust generators (std only, offline), writes everything under `work/`, and compares every produced file with the sha256 in `MANIFEST.tsv` (or, for the intermediate blobs `GD3F2L<rep>R<j>` that are deleted from the Lean tree after use, with `inputs/MANIFEST_v3r.sha256`). Four generator crates (`l5s4o`, `l5reg`, `l5_agg`, `l5hlines`) contain the placeholder path prefix `/DEV_TREE` in their sources; the script patches working copies in `work/patched/` (the sources in `generators/` stay unchanged), so nothing is written into `LEAN_DIR`. **If you change the layout, adjust the path constants in these crates or in the `sed` lines of the script.**
Chain: `l5v3 emit` + `l5v3 v3` (environment `L5V3_PR=300 L5V3_LAYOUT=A`, node chunk 1700; these parameters were found by search against the manifest) -> `GD3N*`, `GD3F2N*`, blobs `GD3F2L<rep>R<j>` -> `l5s4o REP OUTDIR TSVDIR c<j>=GD3F2L<rep>R<j>.lean ...` (chunks in numeric order; the node-side modules must already be in OUTDIR, because the main module imports `GD3N<rep>Z` iff that file exists there) -> `GD3O<rep>`, `T`, `Rc<k>`; `l5qemit emitc T4DIR T4TSV LinTL.lean all plan.tsv OUTDIR LO HI` -> `LinRQSC<k>` for plan lines LO..HI-1; `l5reg gen REP...` and `l5reg mem` -> `L5Reg/Reg<rep>.lean`, `Mem.lean`; `l5_agg gen` -> `AggFive/*`, `L5S5/FiveSpeedFinal`; `l5hlines gen` -> `AggFive/Hl/*`.
Inputs copied into `inputs/` (sha256 in `inputs/INPUTS.sha256`): `plan.tsv`, `t4_classes.tsv`, `src_t4_all/` (T4 class tables written by an earlier run of `l5v3`; these are inputs, not regenerated here), `modname.tsv`, `rollout_results.tsv`, `T2RL_STATUS.tsv`, `extra_built.txt`, `MANIFEST_v3r.sha256`. The steps `reg`, `agg` and `hl` read `LEAN_DIR` (the `L5S4` sources and the `.lake` build, and the library modules that the repository does not ship, such as `L5S4.T2All`), so they need the fully built development tree; **in the repository use `--steps build,v3,s4o,lines`**, which needs only `LinTL.lean`.
`--full` (v3, s4o and lines for all representatives and all 1,053 plan chunks, in batches, files removed after each batch) and `--install` (copy regenerated files that match the manifest into `LEAN_DIR` where absent): this is the route that restores the two omitted families.
**Not covered by `regen_data.sh`** (their generators are shipped as sources only): representatives 265 and 304 of the `l5s4o` family (built by the big-representative and critical-leaf chains; running `l5s4o` on 265 gives different files), representatives 927, 1075, 1336, 1343, 1524 and 1763 (built by an earlier run with 64-record chunks; running `l5s4o` on them gives different files), the T2 families (`l5s4r_gen`, `l5s4s_gen`), `l5s4e_gen`, `l5s4f_gen`, `lean5_wp1` box data, `LinRQSG`/`LinRQSA`/`LinRAll`, `RegP*`, `RegFin*`, and the `l5v3` T4 mode that writes `src_t4_all`. For these the manifest hashes and the shipped sources are the artefact.

## 9. Known gaps
G1 No clean from-scratch build (36.8 h) was done; the development tree was built incrementally over 17 to 19 November 2026 with restarts and forced rebuilds of mirror modules, so the `.olean` set there is not the product of one clean run. G2 No human review of the proof, the statements or the generated-data soundness theorems has taken place (the kernel is the arbiter). G3 The five-speed-specific prior-art search was not repeated on 19 November 2026; only version 1 of Yi, Gill and Bu was read. G4 Representatives 265, 304 and several generator families are not regenerated by script (section 7). G5 Planted-`sorry` controls live in importable library modules of the development tree outside the headline closure (section 2; proposal). G6 Generated modules carry historical step labels in their headers (section 3). G7 The closure has 17,598 modules and no aggregator imports all of them except the final modules: build by module name. G8 The generator sources contain a placeholder path prefix (`/DEV_TREE`); the shell drivers under `generators/drivers/` and the shell scripts next to the generator crates are documentation of the development build and are not runnable as shipped.
